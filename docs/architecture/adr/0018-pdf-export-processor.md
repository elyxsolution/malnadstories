# ADR-0018 — PDF Export Processor: the first concrete, deterministic document exporter

- **Status:** Accepted
- **Date:** 2026-07-24
- **Phase:** 8 (Render Engine & PDF Platform — the first exporter; task-phase 17)
- **Deciders:** Chief Software Architect, Worker V2

## Context

The Document Assembly Platform (ADR-0017) produces an immutable, format-independent Document that
references rendered Page Artifacts by identity, and reserves export to independent processors. This
task-phase builds the first of those: the **PDF Export Processor** — a normal Processor SDK
implementation that converts an immutable Document into a **deterministic PDF Artifact**, while
remaining completely independent of Document construction and page rendering. The Document Platform
is unchanged.

Constraints from the objective: consume immutable Documents; resolve referenced Page Artifacts;
assemble pages into a PDF; embed document metadata; apply print profile settings; produce an
immutable PDF Artifact + a deterministic PDF Descriptor; validate the generated PDF before producing
the Artifact. It must NOT modify Documents, render pages, process images, compose layouts, introduce
business logic, or perform storage/networking. Output must be **byte-identical** for identical
inputs — explicitly normalizing/overriding any timestamps, random ids, object ordering, or
producer/creation metadata a PDF library would introduce. Export configuration (page size, bleed,
crop marks, compression, metadata, PDF version) must be part of export identity. The PDF Artifact
identity derives from Document identity + export config + processor version. Production must go
through the Artifact Platform.

Decisions needed: (1) which PDF engine; (2) how the processor consumes the Document + resolves pages
without rendering/processing; (3) how determinism is guaranteed; (4) how identity + config
participate; (5) how validation gates production; (6) how future exporters follow.

## Decision

**1. A pure-TypeScript deterministic PDF writer — no external PDF library.** The whole platform is
deterministic + dependency-free by discipline, and general PDF libraries inject timestamps, random
`/ID`s, and producer metadata and do not guarantee object ordering. So the exporter owns a minimal
PDF writer that controls object numbering + ordering, writes a byte-accurate xref, uses **no
`CreationDate`/`ModDate`**, a **fixed `Producer`** (pinning the processor version), and a trailer
`/ID` **derived from a SHA-256 of the document body** (never random). This is the same "own the
deterministic implementation, reserve the heavy backend behind a contract" choice made for the
Native Image Backend (ADR-0015) — here it also directly satisfies the byte-identical requirement.

**2. A normal Processor SDK implementation.** `createProcessor(spec, deps)`: input slot `document`
(the canonical Document JSON artifact), output slots `pdf` + `descriptor`. It reads the Document via
the SDK context, `parseDocument`s it (READ-ONLY — the Document is never modified), resolves each page
by `ctx.readKey(page.artifact)` and `decodeRaster` (image-backend's container decode — **format
reading, not image processing**: no resize/rotate/convert/composite), assembles the PDF, validates,
and produces both Artifacts through the SDK's Artifact gateway — so production never bypasses the
Artifact Platform.

**3. Determinism is structural + enforced.** Integer coordinates, deterministic UTF-16BE-hex text
strings, controlled object order, content-derived `/ID`, fixed Producer, no dates. `compression:
'none'` (default) is byte-identical on every platform; `'flate'` (node:zlib, fixed level) is
deterministic given the same zlib. Identical Document + page artifacts + config + processor version
therefore yield byte-identical PDF bytes → an identical content-addressed Artifact.

**4. Export configuration is part of identity.** `page size · bleed · crop marks · compression ·
metadata · PDF version` are parsed + resolved (`parsePdfExportConfig`) and flow into the PDF bytes,
so config changes change the bytes (and thus the Artifact). Because Artifacts are content-addressed,
"identity derived from Document + config + processor version" holds by construction, and the PDF
Descriptor records the derivation explicitly.

**5. Validation gates production — an invalid PDF Artifact is never produced.** `validateExportPages`
(uniform page sizes) runs before generation; `validatePdf` (header/catalog/page objects/xref/EOF)
runs on the generated bytes before produce; the config + Document parsers reject unsupported config
and malformed Documents; a missing/undecodable page reference is a permanent failure. Every failure
is an in-band `StepFailure` (SDK), never a produced Artifact.

**6. A deterministic PDF Descriptor + the pattern for future exporters.** `buildPdfDescriptor` emits
a JSON-safe record (document identity + ordered page identities + export config + PDF version +
processor version) for replay/audit/debug, produced as a second Artifact. Future exporters (preview
images, print packages, archival formats) follow the same shape: an SDK processor consuming the same
immutable Document, owning its own generator, producing through the Artifact gateway.

## Options Considered

1. **Pure-TS deterministic PDF writer inside an SDK processor (chosen).**
2. **Bundle a PDF library (pdfkit / pdf-lib).** Rejected: injects timestamps + random `/ID` +
   producer metadata + non-guaranteed object ordering (fails the byte-identical requirement), and
   adds a heavy dependency to an otherwise pure workspace. A future library-backed exporter could be
   added behind the same processor contract if ever needed, with normalization applied.
3. **Put export logic in the Document Platform / composition.** Rejected: the Document must stay
   format-independent (ADR-0017) and the compositor stays rendering-only (ADR-0016); export is a
   separate, independent processor.
4. **Re-decode/transform page rasters via the image backend's transforms.** Rejected as image
   processing: the exporter only *reads* the page container (`decodeRaster`) and *packs* samples into
   PDF image XObjects (channel selection/de-interleave — no pixel transformation).
5. **Derive the PDF Artifact key directly from `docHash + config + version`.** Rejected: Artifacts
   are content-addressed by their bytes; since the bytes are a pure function of those inputs, the
   content address already reflects them, and the Descriptor records the explicit derivation.

## Consequences

- **Positive:** a deterministic, byte-reproducible PDF exporter that is a clean SDK processor;
  equivalent exports are the same Artifact (content-addressed); config is part of identity;
  validation makes an invalid PDF Artifact impossible; the Document Platform is untouched; the
  exporter is provably free of rendering / image-processing / layout / storage / networking / business
  logic (grep + boundary verified); it establishes the exporter pattern for preview/print-package/
  archival formats.
- **Negative / trade-offs:** the built-in writer is minimal — one image XObject per page filling the
  media box (uniform-page albums; mixed page sizes are rejected), `'none'`/`'flate'` compression only
  (no JPEG/DCT passthrough or downsampling — that would be image processing), crop marks are a fixed
  18pt corner style, and metadata is the core Info fields; richer PDF/X/ICC-output-intent/pre-press
  features are future additive work behind the same processor.
- **Follow-ups / remaining risks:** `'flate'` determinism depends on the platform zlib (default
  `'none'` avoids this); a real pipeline wires the processor into the coordinator's resolver against
  the real content-addressed store and feeds Documents whose pages are real composed page Artifacts;
  additional exporters (preview/print-package/archival) are the next additive work; PDF/X pre-press
  conformance can be layered on later.

## Compliance

Framework-independent SDK processor; strict TypeScript; full unit tests (26 new; `pnpm verify` green
— 662 total, 27 packages). Consumes immutable Documents (read-only) + resolves Page Artifacts;
produces an immutable PDF Artifact + a deterministic PDF Descriptor through the SDK Artifact gateway;
validates before producing (invalid PDF Artifacts never exist). Deterministic: no dates, fixed
Producer, controlled ordering, content-derived `/ID`, integer geometry — byte-identical
(test-proven). Export config is part of identity. No Document modification, no rendering, no image
processing (only format packing), no layout composition, no business logic, no storage/networking
(grep + boundary verified). Boundaries: depends only on foundation leaves + control-plane +
infra-contracts + processing + processor-sdk + document + image-backend (`decodeRaster` only);
nothing depends on this package.
